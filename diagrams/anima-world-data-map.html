01总拓扑：谁读写谁

世界不再是一个文件——很多进程通过同一个 Redis 连上同一个活着的世界，act() / intend() 在一把跨进程的世界锁下执行；历史落在 MySQL，任何一侧都不持有另一侧的拷贝。

02分家判据：带不带得进上下文

Redis / MySQL 的分界不是"冷热"也不是模糊的"增长性直觉"，而是一条可验证的规则——

进得了提示词→必须有界→Redis

LLM 上下文有上限，所以她此刻带在身上的东西按世界规模封顶：黑板每人约 20 键、edges ≤ 2×N²（谓词闭集，承重）。

进不了提示词→可以无限→MySQL

要用时按 k 取回（三因子检索、分页）。四样：events、memories、conversations、messages。

可验性：分对了的话提示词不随世界变老而涨。实测 60 世界日，事件 50 → 3264（×65），提示词 2251 → 2272 字。tests/test_bounded.py 是这道闸。

全部运行时数据的归属。键名省略前缀 anima:{world_id}；MySQL 表名的 {prefix} 让一个库跑多个世界。

04各落点明细

Redis · 运行时状态

前缀 anima:{world_id}: · 多进程共享 · 一把 RedisLock

  • 纯运行时
  • :agent:{id}黑板 hash
  • :clock · :lock时钟 · 跨进程锁
  • :transit · :doing · :plans在途 · 动作 · 规划
  • 世界状态
  • :edges(:id) · :needs · :cliques · :reflection
  • :stance · :mutes · :refused_topics · :followups(:id) · :overrides
  • :stock:{owner} · :stock_owners量
  • :visibility · :stock_places认知层
  • 创世配置与作者意见
  • :locations · :bt_actions · :bt_nodes
  • :item_defs · :shop_stock · :prompts
  • :config · :world_rules · :meta配置 · 规律 · 出生证明/占用标记
  • 转录（无 mysql= 时）
  • :conversations(:id) · :messages(:id) · :conv_msgs:{id}

纪律：只填缺，不覆盖（黑板 seed_missing、时钟 setnx）。黑板曾漏过这条——第二个 World.open 会悄悄把她挪回 cafe，两边都不报错。

MySQL · 无限增长的历史

{prefix} 让一个库跑多个世界（撞表 = 两个世界共用历史）

  • {prefix}eventsMySQLEventLog
  • {prefix}memoriesMySQLMemoryStore
  • {prefix}conversations · {prefix}messagesMySQLChatStore

实测依据：三人世界 20 天，Redis 内存增量的九成是 events + memories；一千个世界一年 4.6 GB 常驻且不回落。

⚠ 传工厂：mysql=lambda: pymysql.connect(…)。pymysql threadsafety=1 而引擎有线程池；裸连接不必现地坏，所以开机当场点名。

⚠ 历史只有一份：events/memories 归 MySQL 后，Redis 里冻在旧时刻的拷贝会被删掉——两份真相里一份不更新是最怕的坏法。

机器配置 · 不随世界走

~/.anima-world/config.json · 0600 · 明文（0600 即边界）

  • llm.api_key唯一的 secret，绝不进世界
  • llm.base_url · llm.model · llm.background.model
  • llm.timeout · llm.max_retries

判据：换一个世界这个值要不要跟着变？不要 → 它是机器的。

环境变量→ 机器配置→ 世界配置（旧世界兼容）→ 默认值

人不手写环境变量：config set 与 start 的引导直接写这个文件。降级永远可见（runtime.llm.degraded_reason）。

进程内 · 有意不落库

派生层与执行机构——可以随进程消失，重建必然正确

  • 记忆投影从事件日志重折
  • RLock + Condition进程内唯一的锁
  • 线程池叙事/规划/关系判定，LLM 永不进 tick 线程
  • scheduler.world_rules开机读入的规律列表
  • LLM 客户端注入；钥匙来自机器配置

判据：能从别处重建的不落库——存两份只多一种不一致的坏法。

核对来源　Redis 键：redis_state.py 全部 KEY_PREFIX 构造点；MySQL：mysql_state.py 的 GROWS_FOREVER 与 SCHEMA；接入纪律：api.py World.open 的 seed_missing / setnx 与 _drop_stale_redis_copies；机器配置：machine_config.py 的 MACHINE_KEYS 与解析顺序。

阅读方式　拿一样数据先问"她带不带得进上下文"：进得了 → 有界 → Redis；进不了 → 无限 → MySQL。加新的量再多问一句：她该不该知道它（认知层）？她会把它带进提示词吗（tests/test_bounded.py）？
