# Agent 运行时:世界没有心跳,时间是动作的副产品

| | |
|---|---|
| 日期 | 2026-07-31 |
| 状态 | **设计,未实施** |
| 起点 | 很多进程操作同一个世界,而每个进程是一个 LLM 驱动的角色 |
| 前置 | `docs/DB-SPLIT.md`(世界文件里只有世界) |

这份文档定下三件事:**时间是什么**、**谁决定行为**、**多进程怎么共处**。

---

## 0. 先记两个实测,它们是这份设计的地基

### ① 连续量是惰性结算的 —— tick 的频率不影响任何结果

```
288 次 tick(1)  →  energy 0.5625  hunger 0.3167  雨天数 1.0
1   次 tick(288) →  energy 0.5625  hunger 0.3167  雨天数 1.0   ← 逐位相同
```

需求曲线和 world-rules 都从量自己的 `updated_tick` 算 `dt`。**给它一个 Δ,它自己算对。**

这原本是为了性能(一万棵树不必每 tick 算一万次),在这份设计里它变成了地基:
**只要能说出"过去了多少",就不需要一格一格地走过去。**

### ② 世界的时间不随真实时间走

```
关闭前:tick=288        …… 停机 ……        重开后:tick=288
```

停机期间世界**一格没动**。这不是缺陷,是这份设计要的性质:
**没人做事,世界就不前进。**

## 1. 时间

> **世界的时间是动作的副产品。没有心跳。**

```
每次有人提交一个动作:
    Δ = 从上一个动作到这一个之间应该流逝多少
    世界推进 Δ(结算连续量、让在途的人到达、跨过门槛发事件)
    然后执行这个动作
```

`Δ` 从动作本身来:走一段路 8 tick、睡一觉 96 tick、说一句话 1 tick。
`tick(n)` 从"心跳"退化成一个内部函数——**推进 Δ**,不再是世界的驱动力。

三个跟着成立的性质:

- **存档就是暂停键。** 世界文件里存着"停在哪一刻",下次谁提交动作就从那儿接着走。
  中间隔了三分钟还是三年,对世界没有区别。
- **没有假历史。** 三天没人在,那三天就是空的——而不是编造出三天的事件。
- **可复现的那部分仍然可复现。** 连续量由 Δ 决定,同样的 Δ 得同样的值。
  不可复现的只有 LLM 的决定本身,而那本来就不可复现。

⚠️ **代价**:"现在几点"不再有全局答案,只有"世界推进到哪儿了"。任何依赖墙上时钟的
东西(比如"每天早上 8 点开店")要改成依赖世界的账。作息本来就是按世界时间写的,
所以这一条影响不大——但要有意识。

---

## 2. 谁决定行为:两档,而且会自动升降

全 agent 化最诱人也最贵。**三个角色没问题,三十个居民就是三十份订阅费在烧,
而其中二十五个人玩家这辈子都不会跟他说话。**

所以分两档:

| 档 | 谁 | 怎么决定 | 成本 |
|---|---|---|---|
| **LLM 档** | 主要角色、被玩家搭过话的、剧情里的 | 独立进程,自己想 | 一次 6.5 秒 + 真钱 |
| **便宜档** | 其余所有人 | 行为树:排班 + 身体 + 打算 三者仲裁 | **0**(实测 0.144 ms/tick) |

**分档不该手工配。** 谁被搭话、谁进剧情,谁就升到 LLM 档;没人理的自动落回便宜档。

这一条顺带给行为树一个明确的位置。此前它是个尴尬的东西——实测它的树深只有 2、
`condition` 节点一个没用,本质是"一张按优先级排序的排班表"。
在这份设计里它不再假装是通用行为树,它是**背景角色的免费版本**,而这个位置是必需的。

---

## 3. 谁唤醒 agent

没有心跳之后,LLM 不会自己开口。必须有东西叫醒她。三个来源:

1. **她自己上一个动作结束了** —— "我走到了,然后呢"。这是主循环。
2. **世界里发生了她感知得到的事** —— 有人跟她说话、身边出事、门槛被跨过。
   **感知层天然就是这个过滤器**:她感知不到的事不该叫醒她。
3. **她自己定的闹钟** —— `delay_reply` 那条路已经是这个形状(`agent_followups`)。

来源 2 是关键,而且它正好是之前记下的那条债:**定时轮次现在是纯时间触发的**
(每 6 世界小时问一次),所以她可能在你进门时发呆、在没人时开口。改成事件唤醒之后
这个问题自己消失。

## 4. 多进程怎么共处:世界是权威,agent 是客户端

```
agent 进程(夏) ─┐
agent 进程(柔) ─┼── 传输 ──▶ 世界进程 ──▶ world.db
人类玩家       ─┘  (Redis)    校验 / 定序 / 推进 Δ / 记账 / 广播
                      ◀── 感知 ──
```

**agent 不共享状态,它们提交动词、接收感知。**

### 为什么不是"多进程共享状态"

试过算这笔账,结论很清楚:

| | |
|---|---|
| 黑板访问 | 每 tick 80 次,一个世界日 22949 次(3 个角色) |
| 逐个访问走 Redis | 1.1~11.5 秒/世界日 |
| **批量读写走 Redis** | **0.13~0.39 秒/世界日 —— 完全可接受** |

**所以性能不是反对理由。** 真正的理由是:批量读写的写法是
「读全量 → 在内存里算 → 写回」,而中间那步"在内存里算"就是"状态在一个进程里"。
两个进程同时做这件事,后写的覆盖先写的,**而且无声**。

更根本的一句:

> **Redis 保证"每条命令原子",而世界需要的是"一个动作原子"。**

这个引擎里有三件事要求动作级原子:world-rules 的双缓冲(同一轮读上一轮的值)、
三源仲裁(身体/排班/打算要基于同一份快照)、`events.seq` 的折叠顺序
(重放能否重建出跑出来的世界,全靠它)。

只有两条路:**状态在一个进程里**(本设计),或者**整个动作逻辑用 Lua 写进 Redis**
(那不是换存储,是换语言重写引擎)。中间没有安全地带。

### 世界进程撑得住吗

撑得住,而且富余六个数量级:

| | |
|---|---|
| 那把唯一的锁,每次持有 | **62 微秒** |
| 一次 LLM 往返 | **6 500 000 微秒** |
| → 一个 agent 等一次模型的时间里,这把锁能过 | **10 万次** |

**瓶颈永远是 agent 那边的网络,不会是世界进程。**

### 陈旧的决定

agent 想 6.5 秒,决定送达时世界已经变了。所以**动词在执行时校验,不在决定时**。

这套模式引擎里已经有了:`walk_away` 执行时才查是否面对面,不在场就降级成挂断;
`reach_out` 执行时才查在场。**继续沿用,不要发明新的。**

## 5. Redis 放哪

**当传输,不当世界。**

| | 放哪 | 为什么 |
|---|---|---|
| 动词提交队列 / 事件广播 / 在线状态 | **Redis** | 它就是干这个的 |
| `llm.*` 配置与密钥、转录、玩家会话 | **Redis 或别处** | 见 `DB-SPLIT.md`,本来就不是世界 |
| 事件、记忆、关系、量、规律、感知声明 | **世界文件** | 一个文件 = 一个世界 |

世界文件为什么不动:`.cyberworld` 导出现在是一行 `source.backup(target)`,新加的表
自动跟着走(验过环回);创作台按引擎版本隔离归档;`DB_FORMAT_VERSION` 在打开文件时
校验,挂错卷当场拒。换成 keyspace 之后这三条都要重建,而**第三条会从"当场拒绝"退化成
"半懂不懂地读下去"** —— 从崩溃变成照跑但给错东西,方向反了。

⚠️ 持久化本身**不是**保留 SQLite 的理由。Redis 的 AOF `appendfsync always` 耐久度
和 SQLite 一个量级,拿持久性说事是糊弄。理由只有"一个世界 = 一个可分发的单位"这一条,
但这一条是产品的承重墙。

## 6. 引擎要改什么(很少)

| 要建 | 在哪 | 大小 |
|---|---|---|
| `World.act(agent_id, verb, params)` —— 外面的人怎么提交动作 | 引擎 | **一个方法** |
| 动词表统一 + 导出(BT 动作 / 工具 / 节拍 op 现在是三套) | 引擎 | 登记与导出,不是重写 |
| 事件唤醒(替换纯时间触发的 autonomy) | 引擎 | 中等 |
| 收动词、推进 Δ、广播事件的循环 | **宿主** | 约 200 行 |
| 队列与广播 | **Redis** | — |

**世界进程本身不用写,它就是今天的 `anima-world run`** —— 只是给它开一扇门。

CLAUDE.md 那条"引擎是纯库,需要网络暴露由宿主自己包一层"在这里恰好是对的:
**世界服务是一个宿主应用,不是引擎的一部分。**

### 三套动词表要先并成一套

| 入口 | 词汇 | 谁导出 |
|---|---|---|
| duty(日课) | `walk` / `work` / `sleep` / `chat` / `eat` / `idle` | **没人** |
| tool(能力) | `walk_away` / `mute` / `broadcast` / … | `contract.chat_tools` |
| beat op(节拍) | `agent_return` / `grant_item` / `pay` / … | `contract.beats.ops` |

三套互相重叠(`walk` / `walk_away` / `agent_return` 都在挪人,而且前两个**已经共用
`move_agent`**),而只有两套被导出。并成一套之后:

- **原子动词**:`walk(location)` / `eat(item)` / `sleep()`
- **复合动词**:具名子树(`open_cafe` = 走过去 + 干活)。**已经存在了** ——
  `bt_nodes` 里 13 个具名 `sequence`,而且 `tree` 列 = agent id,所以
  **"她能做什么"天然按人分**,连作用域机制都不用新造。
- **surfaces 决定谁看得见**:`walk` 只给仲裁器,`open_cafe` 也给 LLM。
  **别把原子动词给 LLM 看** —— 它会去编排脚步,一步一次网络往返,又贵又编得烂。

调用复合动词的语义必须是**设定意图,不是执行到底**——否则身体那道紧急带被架空,
"饿死也要把店开了"会回来。

## 7. 快进变成两种,而且必须分开

现在 `simulate` 把两件事混在一起。之后它们语义不同:

| | 做什么 | 用在哪 |
|---|---|---|
| **静默快进** | 不叫醒任何人,只按 Δ 结算连续量 | 树长了三天,但那三天没人做过事——**诚实** |
| **活着快进** | 真的叫醒 agent,真的花钱 | 创作台的"三日试炼"要看事件,那本来就该花钱 |

现在的 `simulate` 是第一种(它甚至不跑 autonomy——见 CHANGELOG),
但它的名字和文档让人以为是第二种。**分开命名。**

## 8. 我答不了、需要定的

1. **同时到达的动作谁先?** 到达序?轮转?优先级?——单写者让这个问题**有答案**,
   但答案是什么要定。
2. **一个动作要花多少 Δ?** 走路按距离算(已有),说一句话算多久?想一想算多久?
   这直接决定世界的时间流速。
3. **升降档的判据。** "被搭过话"之后多久落回便宜档?落回时她正在做的事怎么办?
4. **一个 agent 进程挂了。** 她卡在半路上——世界该当她还在走,还是当她放弃了?
5. **玩家和 agent 对称到什么程度?** 玩家能不能调 `open_cafe`?(我倾向能——
   `player:阿檀` 和 `agent:夏` 同构是 `DB-SPLIT.md` 里那条灰区的解法。)

## 9. 记两个我在讨论里说错的

这份设计有两处是被纠正出来的,记下来免得再犯:

- **"每 tick 80 次访问搬到 Redis 就是 241× 慢"** —— 错。那是按逐个访问算的,
  没人会那么实现;批量之后 0.13~0.39 秒/世界日,完全可接受。
  **性能从来不是反对共享状态的理由**,理由是动作级原子性。
- **"关掉程序三天,再打开,世界过了三天"** —— 错。实测停机前后 `tick` 一格没动。
  世界的时间只随动作走,不随真实时间走——而这恰好是这份设计要的性质。
