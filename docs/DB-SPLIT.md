# 世界文件里应该只有世界

| | |
|---|---|
| 日期 | 2026-07-31 |
| 起因 | "任何与世界强相关的东西才写到数据库中" |
| 状态 | 移动 1/2/3 已实施(1.4.0);2026-08:**世界文件本身退役** —— 世界只住 Redis,"世界文件里应该只有世界"以"没有世界文件"收官 |

## 判据

一句话就够,而且可操作:

> **把这个世界文件发给另一个人、在另一台机器上打开 —— 它该跟着走吗?**

该 → 它是世界。不该 → 它不该在这个文件里。

`.cyberworld` 分发本来就是这个语义,所以这条判据不是新发明的,是把已有的分发语义
倒推回 schema。

---

## 先说最坏的那一条:世界文件冻结了引擎的默认值

实测(2026-07-31):

```
① 新世界:chat.recall_k = 3
② 假设引擎下一版把这个默认值改成 99(因为 3 被证明太少)
③ 老世界用新引擎打开: 3    ← 还是旧的,永远
④ 新建的世界:        99
```

`seed_defaults` 的 docstring 自己写着:**"Once a row exists, this is a no-op for that
key on every subsequent call — the DB value always wins from then on."**

数出来的量级:

| 表 | 行数 | 其中作者真的动过的 |
|---|---|---|
| `config` | 36 | 内置种子点了 7 个开关,其余 **29 行是默认值** |
| `prompt_templates` | 31 | **0** —— 全部是引擎默认值 |

而且 `config` 的列是 `key,value,value_type,category,is_secret,description,updated_at`
—— **没有任何一列记录"这是谁写的"**。引擎分辨不了作者的决定和创世那天的快照。

后果有三层,一层比一层坏:

1. 世界文件里塞了 60 行不是世界的东西;
2. 引擎改进默认值,**已有的世界一个都吃不到**;
3. 而且**无声** —— 两个世界行为不同,而 `config list` 看上去一模一样,没人会想到去比。

第三条是这个仓库最在意的那类坏:照跑,但给的不是你以为的东西。

---

## 25 张表的分类

### A. 世界本身 —— 必须跟着走(15 张)

| 表 | 是什么 |
|---|---|
| `events` | 唯一真相,审计 = 重放 |
| `locations` | 地图 |
| `memories` / `reflection_state` | 她知道什么 |
| `edges` | 关系 |
| `stocks` | 世界的量 |
| `world_rules` | **这个世界**的物理法则 |
| `stock_visibility` / `stock_places` | 她感知得到什么、东西在哪 |
| `agent_needs` | 身体 |
| `item_defs` / `shop_stock` | 经济 |
| `cliques` | 社群 |
| `bt_nodes` / `bt_actions` | 行为 |
| `db_meta` | 格式戳 |

这些没有争议。

### B. 她和某个人之间的状态 —— 灰区(5 张)

`agent_stance` / `agent_mutes` / `agent_refused_topics` / `agent_followups` /
`persona_overrides`

**事实是世界的**(她真的在不理你、她真的拒绝谈那件事),**但键是宿主给的
`player_id`**。把我的世界发给你,里面写着"她在屏蔽 p1" —— 而 p1 是我这边的一个 id,
在你那边什么都不是。

**建议:留在世界里,但把玩家提升成世界里的实体。** 现在 `player_id` 是一个裸字符串,
到处流窜(`players` 是内存 dict,不落库)。如果玩家是世界里的一个 owner
(`player:阿檀`,和 `agent:夏` / `tree:oak` 同构),那这五张表就名正言顺 ——
她屏蔽的是**世界里的一个人**,不是宿主的一个会话 id。

这一步顺带解掉另一个问题:`stocks` 的 owner 已经支持任意前缀,玩家进来就能有量。

### C. 转录 —— 引擎自己说过它不该在(2 张)

`conversations` / `messages`

CLAUDE.md 白纸黑字:

> 世界只收当轮有限历史(`World.chat` 传入、`record_chat_turn` 回传),
> **完整转录留在宿主应用里,不落世界**。

而这两张表就是转录。纪律和 schema 对不上,已经很久了。

**注意**:1.3.0 把逐轮观测量(stance / intent / tool_call)落在 `messages` 行上,
理由是"聊天子系统与事件核解耦,不该每轮发一个事件"。所以搬走 `messages` 之前,
得先给那些观测量找个新住处 —— 它们**是**世界的(她这一轮选择了赌气),转录不是。

### D. 不是世界 —— 运维与基础设施(混在 `config` 里)

| 键 | 为什么不是世界 |
|---|---|
| `llm.api_key` | **最严重**,见下 |
| `llm.base_url` / `llm.model` / `llm.background.model` / `llm.timeout` / `llm.max_retries` | 你用哪家模型和这个世界是什么样无关 |
| `scheduler.tick_rate` | 这台机器上跑多快 |
| `planner.timeout` / `judge.timeout` / `agent.idle_timeout` / `chat.idle_timeout` | 超时是运行环境的事 |

**`llm.api_key` 那条要单独说**:它是 secret,所以要加密,所以有了
`world.db.key`,所以 CLAUDE.md 才有那条"**Fernet 密钥必须随 db 搬迁**"的不变量,
所以丢了 keyfile 就全线降级 Mock。

**这一整条耦合链的根源,就是把一把 API key 存进了世界文件。** 把 `llm.*` 搬出去,
`world.db.key` 这个东西可以整个消失 —— 世界文件里没有密文了,搬迁不用带钥匙,
也不会有人把自己的 key 打进 `.cyberworld` 发出去。

### E. 引擎默认值 —— 最有害的一类(`config` 29 行 + `prompt_templates` 31 行)

见上。这一类的特点是:**它们看起来像世界数据,行为上却是过期的引擎快照。**

---

## 怎么拆:三步,只有第三步需要 2.0.0

### 移动 1:`config` 与 `prompt_templates` 只存"作者动过的"(1.4.0)

创世时**不写默认值**。读的时候:表里有 → 用表里的;表里没有 → 现场从代码里的默认值取。

- 老世界自动吃到新引擎改进过的默认值
- "这个世界的作者决定了什么"一眼可见(表里剩下的就是)
- 世界文件小 60 行

**为什么这不是格式变更**:老引擎打开一个 `config` 只有 3 行的世界,会跑它自己那套
`seed_defaults` 把默认值补回去,然后照常运行。**加法兼容**,所以跟次版本走。

**已做(1.4.0)。** 实测:毛坯世界 `config` 0 行、`prompt_templates` 0 行;内置种子
(橱窗)的世界 `config` 8 行 —— 正好是作者点亮的那八个开关。拆的路上撞出两个洞,
都是"表里有没有行"被当成了"这个键存不存在":

- **`set()` 没有回落**:新世界的表是空的,于是 `set("llm.api_key", …)` 拿不到
  `is_secret`,**密钥明文写进世界文件,一声不吭**。而 `.cyberworld` 是分发物 ——
  这正是 `machine_config` 那一整轮要防的事,而移动 1 把它的地基抽掉了。
  判据得统一成"引擎声明过什么":`has` / `meta` / `list` / `set` 四个都要回落。
- **搬进 Redis 时整份搬**:`list()` 是合并视图,整份搬过去 = 31 条默认模板全落进
  Redis,刚从 SQLite 拆掉的快照换个后端原样重建,改进过的措辞照样到不了。

**一个诚实的局限:移动 1 只帮到新世界。** 拿真的 1.3.0 和 1.4.0 双向验过:

```
1.3.0 建的世界:  config 36 行 / prompt_templates 31 行
1.4.0 建的世界:  config  8 行 / prompt_templates  0 行   ← 只剩作者点亮的八个开关

1.4.0 打开 1.3.0 的世界 → 照跑,那 36 行照旧生效(source 显示"世界文件")
1.3.0 打开 1.4.0 的世界 → 照跑,老引擎把默认值补回去,作者点亮的一个不丢
```

已有的世界里那 36 行是**真的行**,而 `config` 表没有任何一列记着"这是谁写的" ——
引擎分辨不了"作者设的 3"和"1.3.0 创世那天播的 3"。所以老世界的默认值仍然冻着,
改进过的默认值只到得了 1.4.0 之后建的世界。

不打算自动清理:猜错一次就是悄悄改掉一个跑了半年的世界的行为,而这正是移动 1
要防的那类事。要让老世界跟上,手动删掉没动过的那几行即可。

⚠️ 一个真实的取舍:今天"表里有一行"意味着"值锁死了",这对**可复现性**是有好处的 ——
同一个世界文件在两个引擎版本上行为一致。改完之后,默认值会跟着引擎走。
我认为这是对的(引擎改默认值就是因为旧的不好),但它是个真实的取舍,不是纯赚。
需要可复现的场合,作者显式写进种子的 `config` 即可 —— 那本来就是"作者的意见"。

### 移动 2:`llm.*` 与运行期参数搬出世界文件(1.4.0)

搬到 `~/.anima-world/config.json`(或环境变量 / 宿主注入)。

- **`world.db.key` 可以消失** —— 世界文件里不再有任何密文
- 分发 `.cyberworld` 不可能再泄漏作者的 key
- 多个世界共用一套 LLM 配置,而不是每个世界各存一份

**为什么这也不是格式变更**:老引擎打开一个没有 `llm.api_key` 行的世界 →
补一个空行 → 降级 Mock 并**点名**(启动警告 / `doctor` / `state()` 三处都有)。
不崩,只是降级 —— 而降级看得见本来就是设计。

### 移动 3:转录搬出世界 —— **做完了,但不是这么做的**(1.4.0,加法)

计划是"删两张表、升 2.0.0"。实际做出来的是另一条路,而且更好:

**`conversations` / `messages` 的表还在,只是可以不用。** `World.open(mysql=...)`
把转录接到 `MySQLChatStore`,不给 `mysql=` 就照旧走 SQLite。没有任何列义变化,
老引擎打开这个文件照样跑 —— 所以它是**加法**,跟着次版本走,不需要 2.0.0。

"前置条件:先给逐轮观测量找个新住处"这一条**被否决了**。观测量(stance / intent /
tool_call)是**关于那一条消息的判定**,它和消息同生共死:消息搬到哪儿,它就该在哪儿。
为它单独造一张表,等于让"她这一轮赌了气"和"她这一轮说了什么"住在两个后端上,再拿
message_id 跨库 join —— 那是拿一个真问题换一个更难的问题。

顺带修掉一个洞:那两个方法原本挂在 `ChatStateStore` 上,而它碰的是 `messages` 表。
Redis 版一继承就带着一条指向 SQLite 连接的死路 —— **开了 `chat.stance.enabled` 的
Redis 世界会当场 AttributeError**。现在 SQL 住在表的主人那儿(`ChatStore` /
`MySQLChatStore`),`ChatStateStore` 只转发。

### 判据走了三版,最后一版是可验的

搬的时候量出来一件没预料到的事。世界搬进 Redis 之后,一个三人世界:

```
 世界日     Redis 内存    增量      占大头
   1天        997 KB     +30 KB   events=18KB
  20天       1228 KB    +129 KB   events=158KB memories=77KB
```

**只有 `events` 与 `memories` 随时间线性增长**,20 天里占了内存增量的九成。每世界日
13 KB,一千个世界跑一年 **4.6 GB 常驻**,而且永远不回落。别的东西随**世界的规模**
有界(黑板每人 20 个键,地图创世后不动),不随时间涨。

这是第二版判据(第一版是"这是不是世界",它拆不动转录 —— 转录当然属于这个世界,
只是不该在内存里)。而**第三版更锐,是用的人给的**:

> Redis 其实是做 agent 的记忆等功用,这样做有个巨大的好处是本身 LLM 上下文
> 就是有上限的,这样可以保证对齐。

两个"有上限"是同一个上限。所以:

    进得了提示词的  →  必须有界  →  Redis
    进不了提示词的  →  可以无限  →  MySQL(要用时按 k 取回来)

第三版最好用,因为它**可验**。分对了的话,提示词就不该随世界变老而增长 —— 实测同一个
角色跑到第 60 个世界日:

```
 世界日   提示词    MySQL 记忆   MySQL 事件
   0天    2251字        10          50
   5天    2286字        66         329
  20天    2281字       223        1119
  60天    2272字       612        3264      ← 后端涨 61 倍,提示词纹丝不动
```

`tests/test_bounded.py` 是这道闸(变异验证:拿掉记忆检索的 k,提示词 2275→6546 字,
当场红)。三版判据不互相推翻:第三版解释了前两版为什么大致管用 —— **有界的东西才带得进
一个有上限的上下文**。

分家后实测(同一个世界,同一份负载):

```
 世界日   Redis 增量   MySQL 事件
   1天      +52 KB         105
  10天      +53 KB         559
  20天      +70 KB        1085
  40天      +70 KB        2067      ← Redis 不再涨了
```

三十个聊天回合(60 条消息 2271 字)之后:MySQL 收下全部,**Redis +0 KB,SQLite +0 KB**。

### 顺着第三版改正了一张分错的表:`edges` 不进 MySQL

关系边一度被分进 MySQL,是照着"像不像历史"分的 —— 它看起来是关于过去的事实。
但它有 `UNIQUE(subject, predicate, object)`,谓词是**闭集**(`friendship` / `rivalry`,
`scheduler.py` 里写死的两个),主宾都是 `agent:<id>` —— 上界 2×N²,**按世界的规模封顶,
不按时间涨**。

它属于 Redis。把它放进 MySQL 等于把一个**有界的热读**(每次拼提示词的 relation 块都要读)
放进最慢的后端。

那个闭集是**承重的**:哪天让 LLM 自己说"她们之间是什么关系"(很自然的一步),边就不再
有上界,这笔账要重算。`test_bounded.py` 盯着**这个前提本身**,而不是等它出事。

## 建议的顺序

1. **先做移动 1**。它值钱、是加法、而且解掉的是"世界在悄悄用过期的默认值"这个
   无声的错 —— 这个仓库最在意的那一类。
2. **再做移动 2**。它让一条不变量整个消失(`world.db.key`),这种收益很少见。
3. ~~移动 3 攒到 2.0.0~~ —— **已做,而且是加法**(见上)。判据从"这是不是世界"
   换成"她带不带得进上下文"之后,答案变了:不必删表,只需给它一个不在内存里的去处。

顺带:B 组那条"把玩家提升成世界里的实体"和 §动词表统一是同一个方向 ——
`player:阿檀` 和 `agent:夏` 同构之后,"她能对谁做什么"就不再有两套规则。
